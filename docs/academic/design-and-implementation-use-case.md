# Design and Implementation: Use Case Diagram

Figure X presents the resident-focused use case diagram for DengueWatch. The diagram models only the functions implemented in the current prototype and therefore excludes the health officer workflow from the main system scope. This boundary is deliberate: officer-side investigation, field verification, and operational data-gathering requirements were not fully specified for the present implementation and would weaken the academic accuracy of the diagram if represented in detail without evidence from the built system.

The primary actor is the `Resident / Public User`, who interacts with the system to learn about dengue breeding habitats, explore public reports and hotspots, inspect report details, submit a breeding habitat report, and track report status by reference number. A specialized actor, the `Authenticated Resident`, extends this role with account-based functions such as signing in, saving reports to personal activity, viewing activity history, and removing saved entries.

The report-submission use case is the core interaction in the implemented system. It includes the capture or upload of image evidence, acquisition and confirmation of location, acceptance of public-sharing consent, AI-based habitat pre-checking, nearby-report matching, and generation of a reference number. The nearby-match flow also supports an `Add observation to existing nearby report` extension, which reflects the implemented stacking behaviour used to reduce duplicate submissions around the same location.

Three supporting external actors are shown because they influence implemented behaviour but are not internal system users. The `Identity Provider` supports resident authentication, the `Device Location Service` supports geolocation capture and confirmation, and the `iDengue Registry` supports nearby hotspot and matching context. Including these actors improves the precision of the model by separating external services from internal DengueWatch responsibilities.
